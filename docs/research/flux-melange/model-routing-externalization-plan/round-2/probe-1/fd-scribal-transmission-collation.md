# fd-scribal-transmission-collation — round 2

## Findings Index
- [P1] policy-hash-witness-orphaned — `Decision.PolicyHash` is a persisted exemplar-fingerprint field that already exists in `internal/routing/decision.go` but is never populated by any writer today, and the plan's Phase 2/3 decision function doesn't say whether it inherits it (§phase 2 lines 68-74, §phase 3 lines 76-82)
- [P1] judgment-tag-has-no-scribe — the `judgment` provenance tag (distinct from `unknown`) records a human-typed capability value with no field for who typed it or what session/PR introduced it — an emendation with no colophon (§design principles line 36)
- [P2] registry-refresh-drift-report-has-no-adjudication-path — Phase 6's drift report is specified to detect divergence between two witnesses (registry vs. interrank) but the plan names no resolution rule for when they disagree (§phase 6 lines 99-104)

## Findings

### policy-hash-witness-orphaned
- **Severity:** P1
- **Where:** `internal/routing/decision.go` lines 29, 53, 95, 110, 151, 180, 223, 287 (field defined, written-through, read-back — but never assigned a real value anywhere in the package); plan §Phase 2 (lines 68-74), §Phase 3 (lines 76-82)
- **What:** The codebase already has the collation apparatus this lens is looking for, half-built and unused. `Decision.PolicyHash` is a `*string` column that exists precisely to let a stored decision be checked against the policy text that produced it — the mechanical equivalent of a scribe noting which exemplar she copied from. I grepped every call site: it is threaded through `Record`, `Get`, and `List` faithfully, but no code anywhere in `internal/routing` ever *computes* a hash and passes it in as `RecordDecisionOpts.PolicyHash`. It is currently always empty. The new plan (Phase 2's decision function signature `(role, task_class, constraints, harness) → (model@deployment, effort, verification_gates[], rationale)`, Phase 3's `ic route explain`) never mentions this field. Two readings are equally plausible to a conscientious implementer: (a) wire `PolicyHash` to `sha256(routing.yaml bytes)` so every decision row is a verifiable witness of which exemplar-copy of the policy produced it, enabling exactly the collation the lens wants (detect: did decision X get made against v3 of routing.yaml, or a locally-edited fork nobody committed?); or (b) leave it dead, in which case the plan should say so and remove/deprecate the column rather than silently continuing not to populate a field named for the exact concern this review raises.
- **Evidence:** `grep -rn "PolicyHash\|policy_hash" internal/routing/*.go | grep -v _test.go` returns only the struct/SQL plumbing in `decision.go` — zero assignment sites. `rationale` in the Phase 2 decision-function tuple is a new, unrelated field name; nothing connects it to `PolicyHash`.
- **Suggestion:** Add one line to Phase 2's acceptance criteria: "decision function populates `PolicyHash` = hash of the loaded `routing.yaml` bytes; `ic route explain` prints it." This is the smallest possible fix that turns a decision record into a self-authenticating witness — the exact collation primitive the archetype-recoverability concern (P0 in this lens) needs, and it already has a column waiting for it.

### judgment-tag-has-no-scribe
- **Severity:** P1
- **Where:** plan §Design Principles line 36: "Every value tagged `benchmark | judgment | unknown`."
- **What:** This is a different clause from the "unknown treated conservatively" passage already flagged hot — that finding is about what the router *does* with `unknown`. This finding is about the `judgment` tag itself, which the plan treats as a peer of `benchmark` but which is structurally the conjectural-emendation case the whole lens exists to catch. A `benchmark` value traces to a citable run (Terminal-Bench 2.1, SWE-Bench Pro — both named in the Problem section with numbers). A `judgment` value is, by construction, someone's private reading of the evidence rendered into a number with no attached exemplar: no author field, no date, no linked discussion, no distinguishing it later from a different person's different judgment call about the same axis. Six months from now, when `openai/gpt-5.6-terra@api`'s `discernment: 0.6 (judgment)` looks wrong, there is no way to tell who wrote it, what they were looking at, or whether a second `judgment` value for the same cell from a different session should overwrite it or be flagged as a variant reading. This is precisely "conjectural emendation" — a copyist filling a gap the exemplar (the benchmark suite) left, rendered plausible and permanent by sitting in the same schema slot as a benchmark-backed fact.
- **Evidence:** Design Principles line 36 lists the tag enum with no accompanying metadata fields (no `judged_by`, `judged_at`, `rationale` for judgment rows specifically — Phase 1's schema list, lines 58-60, doesn't mention one either, and Phase 6's drift report (lines 101-104) only cross-checks against interrank, which by definition has no opinion on `judgment`-tagged axes since those aren't benchmarked).
- **Suggestion:** Require `judgment`-tagged registry values to carry `judged_by` + `judged_at` (or a doc-link) alongside the value, and have Phase 6's drift report flag `judgment` rows that are >N days old for re-review — the same staleness-reminder pattern the routing-overrides PRD already uses for human overrides (F5, ">90 days old" reminder), just applied to capability judgments instead of exclusions.

### registry-refresh-drift-report-has-no-adjudication-path
- **Severity:** P2
- **Where:** plan §Phase 6 (lines 99-104): "Add a registry-refresh script cross-checking registry cost/benchmark values against interrank, flagging drift (does not auto-write; provenance stays explicit)."
- **What:** This is the one place in the plan that actually proposes a collation step — two independent witnesses (the hand-maintained registry, and interrank's snapshot) are compared and divergence is surfaced. That's the right shape. But the plan stops at "flagging drift" with no stated adjudication rule: when the two disagree, which one is presumed correct pending human review, and does the flag distinguish "registry is stale" from "interrank is stale" from "they're measuring different deployments under the same name"? Without a stated default, whoever triages the drift report each week supplies their own tie-break silently, and two different triagers over time could resolve the same class of drift in opposite directions with no record of the rule they applied.
- **Evidence:** Lines 101-104 (all of Phase 6) contain no adjudication language; "does not auto-write; provenance stays explicit" only says who does *not* write, not what a human reviewing the flag should presume.
- **Suggestion:** One sentence: "Drift report presumes interrank (benchmark-sourced) wins for `benchmark`-tagged fields; registry (hand-maintained) wins for `judgment`-tagged fields; both are shown side-by-side either way." Small addition, closes the tie-break gap.

## Verdict
Two P1s here are genuinely new: the codebase already contains an unused exemplar-fingerprint column (`PolicyHash`) that is exactly the collation primitive this lens looks for, and the plan's `judgment` provenance tag is a clean case of conjectural emendation with no colophon that the already-hot "unknown" discussion doesn't cover. The P2 sharpens Phase 6's drift report — the plan's one real collation step — by naming a tie-break default. No further findings surfaced beyond these three without drifting into already-hot territory.
