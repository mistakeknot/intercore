## Findings

### version-degrade-policy-conflates-safety-and-nonsafety-fields
- **Severity:** P1
- **Where:** §Risks line 121 ("consumers ignore-with-warning on unknown versions"), §Phase 1 line 58 ("graceful degradation... per the routing-overrides contract precedent")
- **What:** Two round-1/round-0 findings both target this line and were flagged as a contradiction to adjudicate: f-013 (coppice, P3) says the ignore-with-warning policy is unbounded standing-deadwood needing a sunset/ratchet; f-007 (pilotage, P1) says the policy is unsafe *by construction* because it's copied from an exclusion-list precedent (safe to fail open) and applied uniformly to `routing.yaml`, which the same plan (line 37) declares carries fail-closed trust-zone constraints. This is not an irreducible taste call. f-007 wins on two independent grounds:
  1. **Grounding.** f-007 checked the actual borrowed mechanism and found it doesn't exist where claimed: `grep -n "version" internal/routing/*.go` returns zero real matches (confirmed independently in this adjudication — only a doc-comment hit on an unrelated `InferCategoryExported` function). The "routing-overrides contract precedent" cited at line 58 lives entirely in `docs/prds/2026-02-15-interspect-routing-overrides.md` F1, whose actual version-check contract (confirmed by direct read) is: unknown version → "log warning... and proceed *without exclusions*." That precedent's blast radius is bounded by design — the worst case is flux-drive runs an agent it would have excluded, i.e., *more* review, not less. `routing.yaml` in this plan is a different kind of file: it is the single artifact carrying both non-safety fields (capability vectors, cost, effort tables) and the safety-critical trust_zone/constraint/verification-gate rules (line 37: "Fail closed. Encodes the argus-adjacent discipline mechanically"). A version mismatch that makes an adapter "proceed" on this file doesn't fail toward more scrutiny — for the trust-zone fields specifically, "proceed with best-effort parse" is functionally "route unconstrained," the exact inversion of fail-closed.
  2. **Priority/subsumption.** f-013's complaint (no sunset, no escalation-to-error ratchet, unbounded across consumers) is real but is a lifecycle refinement that applies cleanly only once the policy is correctly scoped. If the fix is "split degrade-open (non-safety) from degrade-closed (safety fields)" — as f-007's own suggestion states — then f-013's sunset/ratchet concern still applies, but only to the non-safety half, and at reduced stakes (P2/P3-appropriate: staleness of capability data, not silent trust-zone bypass). Applying f-013's sunset-ratchet fix *without* first applying f-007's split would leave the actual hazard in place: a "warn-then-fail-after-N-versions" ratchet on a *uniform* policy still degrades open on trust-zone fields for versions 1..N-1, which is exactly the window f-007 flags as unacceptable regardless of duration — one client-confidential task routed unconstrained during that window is the whole failure, not a rate that needs bounding.
- **Evidence:** `internal/routing/config.go` (LoadConfig, lines 84+ per f-007) — verified in this session: `grep -rn "version" internal/routing/*.go` and `grep -rln "Version" internal/routing/` both return no structural version field, confirming f-007's grounding claim still holds against current repo state. `docs/prds/2026-02-15-interspect-routing-overrides.md` F1 bullet 3 (read in full this session): "If `version > 1`, log warning... and proceed without exclusions" — confirms the borrowed precedent's fail-open semantics are scoped to an exclusion list, not a fail-closed trust boundary. Target plan line 37 (`routing.yaml` "Fail closed") and line 121 (blanket "ignore-with-warning") are in the same document, same file, no field-level carve-out — the conflict is internal to the plan, not manufactured by the reviewers.
- **Suggestion:** Adopt f-007's split as primary fix in Phase 1's contract spec: non-safety fields (capability vectors, cost, effort mapping) degrade open with a warning, matching the borrowed precedent; safety fields (trust_zone, constraint rules, verification gate requirements) degrade *closed* — an adapter that can't parse a `routing.yaml` version refuses to route rather than routing unconstrained. Then layer f-013's sunset/ratchet concern on top, scoped to the non-safety-field warn-open path only (e.g., "warn for 1 version behind, escalate to hard failure at 2+ versions behind" for capability/cost data). One acceptance bullet in Phase 1 covers both: "version mismatch handling is field-class-aware (safety fields fail closed, non-safety fields warn-and-degrade with a bounded staleness window)."

### f-013s-own-disagreement-note-understates-the-conflict
- **Severity:** P2
- **Where:** heat-ledger.jsonl entry f-013, `disagreement_refs: ["f-007"]`, evidence field: "Distinct from f-007... this finding is about the degradation policy being unbounded over time... not the fail-open-vs-fail-closed safety-semantics concern. Same location, complementary-not-contradictory causes."
- **What:** f-013's own ledger entry self-adjudicates the tension away as "complementary-not-contradictory," but this is only true in the post-fix world where f-007's safety/non-safety split has already been adopted. Read against the plan *as currently written* (uniform policy, no split), f-013's P3 framing ("this is the degradation policy itself being unbounded standing exemption") implicitly treats the blanket policy as a reasonable-but-unbounded steady state worth adding a sunset clause to — which presupposes the uniform policy is otherwise fine to degrade-open indefinitely, the exact premise f-007's grounding falsifies for the trust-zone subset. The two findings don't just look at different axes of the same line; f-013's lower severity (P3 vs P1) and its "add a ratchet" suggestion, taken alone and applied first, would ship a plausible-looking fix (warnings-become-errors-after-N-versions) that still leaves client-confidential routing decisions silently unconstrained during the warning window — the ledger's "complementary" framing risks under-prioritizing the actual P0-adjacent gap in a synthesis pass that dedupes by cluster_id and could pick f-013's milder framing as "coverage achieved" for this location.
- **Evidence:** heat-ledger.jsonl f-013 `severity: "P3"`, `risk.product: 2` vs f-007 `severity: "P1"`, `risk.product: 6` — same location, 3x risk-product spread, and f-013's own text acknowledges "Same location" while asserting non-contradiction without checking whether its suggested fix (sunset ratchet on the uniform policy) would leave f-007's hazard live during the ratchet's own grace window.
- **Suggestion:** In synthesis/dedup, do not let f-013's "complementary" self-tag cause it to fully absorb or downrank f-007 at this cluster. Keep both, sequenced: f-007's field-class split is the P1 structural fix; f-013's sunset/ratchet is a P2/P3 refinement applied only to the post-split non-safety path.

## Verdict
Not an irreducible taste call. f-007 (pilotage) holds: it is better grounded (verified the actual `internal/routing/config.go` has no version field today, and read the actual precedent PRD to confirm its fail-open semantics are scoped to a low-stakes exclusion list), correctly scoped (identifies that `routing.yaml` uniquely mixes safety and non-safety fields, unlike the precedent it's borrowed from), and higher-consequence (degrading open on trust-zone constraints inverts the plan's own stated fail-closed guarantee, a single-instance failure, not a rate to bound). f-013 (coppice) is not wrong, but it is a lifecycle refinement that presupposes the uniform policy as an acceptable base case to add a ratchet to — apply f-013's fix alone and the trust-zone hazard f-007 identifies survives inside the grace window. Correct resolution: adopt f-007's safety/non-safety field split as the primary Phase 1 fix, then apply f-013's sunset/ratchet only to the non-safety (capability/cost) side. The heat ledger's own "complementary-not-contradictory" self-classification on f-013 is technically true post-fix but risks under-prioritizing f-007 if read as license to treat both as equally weighted parallel suggestions in synthesis.
