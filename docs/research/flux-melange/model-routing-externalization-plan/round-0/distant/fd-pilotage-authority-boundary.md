## Findings

### verification-gate-is-advisory-not-enforced-by-contract
- **Severity:** P0
- **Where:** §Phase 4 (lines 84-90), §Risks table row "Reward-hacking slips past verification gates" (line 125)
- **What:** The plan's own risk table names this exact hazard and "mitigates" it by asserting: "Gates are router *output*; enforcement lands in adapters (Phase 4) with behavioral-verify, not tests-green." This is the pilot marking a hazard on the chart — the router *names* the required verification (e.g. `behavioral-verify` for elevated reward_hack_risk targets) — but the master (each harness adapter) is the one who must actually steer around it, and nothing in the contract lets a downstream consumer of a decision (interspect evidence, a status report, a human reviewer) detect *after the fact* whether an adapter that received a decision naming `behavioral-verify` actually ran it before accepting the executor's output. Three adapters (Clavain, Codex, Hermes) each independently "apply the decision" (Phase 4 line 87, Phase 7 line 111); if one adapter's author reads the gate name and wires it up correctly and another treats it as advisory prose (exactly what an LLM-authored adapter under time pressure would do), the same routing decision produces safe behavior at one port and unsafe behavior at another — and the contract has no way to notice. This is the single highest-risk seam in the whole design given that Sol is explicitly flagged (Problem section, line 17) as METR-elevated reward-hacking risk: the gate meant to catch exactly that behavior is the one link in the chain with zero verification of its own enforcement.
- **Evidence:** Risks table line 125 states the mitigation as a division of labor, not a check. Phase 4 acceptance (line 90) is "grep confirms no residual hardcoded model-name routing logic in clavain command/agent docs" — this verifies routing logic was *removed*, not that verification-gate *enforcement* was *added or is checkable*. Phase 5's evidence schema (line 94, "executor_failure, validator_rejection, cost_anomaly, constraint_block") has no event type for "verification gate named but not run" or "gate ran and passed/failed" — so even after the fact, interspect's feedback loop cannot detect an adapter that silently drops gates.
- **Suggestion:** Add a fifth evidence event type in Phase 1 (`gate_enforcement`, recording which gate was named and whether the adapter reported running it) and require every Phase 4/7 adapter acceptance criterion to include "evidence emitted confirms gate ran" not just "decision applied." This turns an unenforceable prose mitigation into an auditable one without adding new runtime machinery — reuses the evidence pipe already being built in Phase 5.

### version-degradation-policy-undefined-for-security-fields
- **Severity:** P1
- **Where:** §Risks table (line 121: "consumers ignore-with-warning on unknown versions"); §Phase 1 (line 58, "graceful degradation... per the routing-overrides contract precedent")
- **What:** The plan borrows "graceful degradation and env-var path override per the routing-overrides contract precedent" from `docs/prds/2026-02-15-interspect-routing-overrides.md`, whose F1 spec says: "If `version > 1`, log warning... and proceed without exclusions." That precedent is safe *only* because the thing being degraded-away is an exclusion list — losing it fails open toward "run more review," a quality regression, not a safety one. This plan's `routing.yaml` carries trust-zone constraints (client-confidential → local/approved-vendor, fail closed) in the *same* file. A blanket "ignore-with-warning on unknown versions" policy, copied uncritically from the exclusion-list precedent, means a routing.yaml version bump that a stale Hermes-on-zklw binary doesn't recognize could cause that binary to silently fall back to a no-constraint decision path — the opposite of fail-closed, arrived at via version skew rather than a decision-time bug. Compounding this: I checked `internal/routing/config.go`'s current `LoadConfig` — there is no `version` field anywhere in the config struct today (grep confirms zero matches), so the "precedent" isn't even proven inside intercore's own routing package; it exists only in interspect's unrelated file format.
- **Evidence:** Risks table line 121, generic "ignore-with-warning" policy stated once for the whole contract, no field-level carve-out. `internal/routing/config.go` lines 84-128 (`LoadConfig`): no version field, no version check exists in the actual mechanism being extended — confirmed via `grep -n "version" internal/routing/*.go` (zero hits). The routing-overrides precedent (`docs/prds/2026-02-15-interspect-routing-overrides.md`, F1 bullet 3) is explicit that version mismatch degrades to "proceed without exclusions" — an intentionally low-stakes failure mode, not applicable as-is to trust-zone constraints.
- **Suggestion:** Split the version-degradation policy in Phase 1's contract spec into two classes: non-safety fields (capability vectors, cost, effort table) degrade open with a warning per the borrowed precedent; safety fields (trust_zone, constraint rules, verification gate requirements) degrade *closed* — an adapter that can't parse a routing.yaml version must refuse to route rather than route unconstrained. One additional sentence in the Risks table row and one acceptance bullet in Phase 1.

### no-conformance-obligation-defined-for-third-harness
- **Severity:** P1
- **Where:** §Phase 4 (lines 84-90); §Phase 7 (lines 106-115)
- **What:** Phase 4 builds two adapters (Clavain, Codex) with a shared author and shared review context — de facto conformance by construction. Phase 7's framing even calls Hermes "the validating case for the whole externalization: a harness that cannot read Clavain markdown" (line 108), correctly identifying that this is the test of whether the contract *actually* travels. But the plan never states what a third adapter must *prove* before its fail-closed claims are trusted — there's no conformance checklist, no shared test harness against the routing-contract spec, nothing an adapter author (or a reviewer) can run to confirm "this adapter honors the same no-go channels as Clavain's." Phase 7's acceptance criterion ("constraint block demonstrated live," line 115) is a single positive demo of one scenario, not a conformance suite — it proves the happy path for the one trust-zone case tested, not that Hermes's adapter can't be silently reopened by an unanticipated task descriptor shape Clavain's adapter never exercised.
- **Evidence:** Phase 4 acceptance (line 90) is Clavain/Codex-specific ("grep confirms no residual hardcoded model-name routing logic in clavain command/agent docs" — a Clavain-only check). Phase 7 acceptance (line 115) is a single live demo, not a rerun of Phase 4's conformance bar against the new harness. No shared "adapter must pass X to claim conformance" artifact appears anywhere in the seven phases.
- **Suggestion:** Phase 1's contract spec (line 56) should include a conformance checklist/test vector set (the "three canonical task descriptors" already mentioned at line 64, extended with 2-3 constraint-violation descriptors) that *every* adapter — including future ones beyond Hermes — must round-trip correctly before being trusted. Reuses the canonical-descriptor concept already in the plan; doesn't add new scope.

### safe-harbor-on-no-eligible-model-unspecified
- **Severity:** P1
- **Where:** §Phase 3 (lines 76-82)
- **What:** Phase 3 distinguishes exit codes for "constraint violation ≠ malformed input ≠ no-eligible-model" (line 80) — good hazard differentiation, like marking distinct classes of no-go water. But the plan never states what the *calling harness* is obligated to do upon receiving each. For "no-eligible-model" specifically (e.g., a client-confidential task where no local/approved-vendor deployment is registered) — is the harness required to halt and escalate to a human, or is silently proceeding with *some* model (the harness's own prior default, bypassing routing entirely) an acceptable fallback? The pilotage risk: a harness whose `ic route` call errors non-zero might have pre-existing model-selection logic (Codex's `--config`, Claude Code's `model` param mentioned in Non-Goals line 47) it can fall back to *without* going through the router at all — precisely the "re-fragmentation" the architecture decision (line 26) says the design exists to prevent, and precisely a case where a no-go channel becomes advisory the moment the router can't answer.
- **Evidence:** Phase 3 line 80: exit codes are typed but their *consequences at the call site* are unspecified. Non-Goals line 47 confirms each harness retains its own native model-invocation knobs, which is exactly the fallback path that could be silently exercised on a router error instead of halting.
- **Suggestion:** Add one acceptance bullet to Phase 3 (or Phase 4, since it's adapter-facing): "on `no-eligible-model` or `constraint-violation` exit, adapters MUST NOT fall back to native model selection; they surface the block to the calling flow (human-visible or task-failure), never silently substitute an unrouted model." Names the safe harbor explicitly instead of leaving it implicit in "fail closed" language used elsewhere.

### execution-venue-wall-has-no-enforcement-mechanism-named
- **Severity:** P2
- **Where:** §Non-Goals (line 45)
- **What:** "Execution venue selection... harness-internal concern... deliberate scope wall" is a clean boundary in prose, matching the pilot/master split (pilot advises passage, never touches engine controls). But nothing in the Phase 1 schema spec (roles, task classes, constraints, escalation rules — line 58) names a field that must *not* exist, so there's no check preventing scope creep — e.g., a future `trust_zone: local` constraint being interpreted by an adapter author as "and therefore also pick the Docker sandbox," blurring the line the plan explicitly wants to hold. This is lower severity than the others because it's prose-enforced today and the plan is explicit about intent, but distant-lens value is in flagging that intent alone doesn't stop three independent adapter authors from reading `trust_zone` as a venue hint.
- **Evidence:** Non-Goals line 45 states the wall; no corresponding "MUST NOT" schema constraint appears in Phase 1's three schema definitions (lines 56-63).
- **Suggestion:** One documentation sentence in Phase 1's routing-contract spec: "trust_zone and other constraints describe eligibility, never venue; adapters MUST NOT derive sandbox/execution-target selection from any routing.yaml or decision field." Cheap, prevents drift before Phase 7 forces the issue.

## Verdict
The plan's most dangerous gap is that verification gates and trust-zone fail-closed behavior are both *decision-time* guarantees enforced entirely by adapter goodwill, with no evidence-side check that any given adapter actually honored them — exactly the failure mode where "the same correct decision produces safe behavior at one port and unsafe behavior at another." Given Sol's flagged reward-hacking risk motivates the whole gate mechanism, an unenforceable P0 there deserves a schema-level fix (one new evidence event type) before Phase 4 ships, not after Phase 7 discovers it the hard way.
