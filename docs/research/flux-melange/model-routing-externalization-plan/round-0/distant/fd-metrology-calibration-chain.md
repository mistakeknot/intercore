## Findings

### no-recertification-cadence-for-benchmark-values
- **Severity:** P1
- **Where:** §Design Principles ("Capability vectors with provenance") + §Phase 6 (lines 36, 99-104)
- **What:** Every capability axis is tagged `benchmark | judgment | unknown`, and the plan treats `unknown` as safely conservative. But `benchmark` is not a state, it's a stamp with a hidden expiry — the plan never says how often a `benchmark`-tagged value must be re-verified against its source, or what disposition applies when the cadence lapses. Phase 6 adds a "drift report" that "flags drift" against interrank, but nothing defines the trigger interval (per model release? per quarter? on interrank refresh only?) or what a `benchmark` tag means the day *after* the underlying eval suite version changes (e.g. Terminal-Bench 2.1 → 2.2). Concretely: Sol's Terminal-Bench 2.1 score of 88.8 (cited in the Problem section, line 13) is presumably the seed row's certified value — but there's no field recording that this number is bound to eval-suite version 2.1, and no rule saying it must be re-checked when 2.2 ships. A `benchmark`-tagged row six months stale is indistinguishable, by schema, from one certified yesterday.
- **Evidence:** Design Principles line 36: "Every value tagged `benchmark \| judgment \| unknown`. Router treats `unknown` conservatively; absence of a benchmark score is information." — this only addresses the *absence* case. Phase 6 acceptance (line 104): "drift report runs clean against seed registry" — "runs clean" implies a pass/fail check exists, but Phase 6's own bullets (lines 100-103) never define the check's cadence or failure semantics beyond "flagging drift" and "not auto-writing."
- **Suggestion:** Add one field to the capability-vector schema in Phase 1: `certified_against` (eval-suite id + version) and `recert_due` (date or "on-suite-bump"). Phase 6's drift script diffs `certified_against` against interrank's current suite version, not just the raw score. One diff hunk on the Registry v1 schema bullet (line 59), not a new phase.

### shim-equivalence-table-uncited
- **Severity:** P1
- **Where:** §Phase 2 (lines 68-74), grounded against `internal/routing/routing.go` (current `ModelTier` enum, lines 6-15) and `internal/routing/resolve.go` (`applyFloor`, lines 136-157)
- **What:** Phase 2 promises "retain `ParseModelTier` as a compat shim mapping legacy names to registry entries (existing consumers keep working)." Today `ParseModelTier` maps four bare strings (`haiku`, `sonnet`, `opus`, `fable`) to an ordered int enum, and `applyFloor` in resolve.go does an integer comparison (`floorTier == TierUnknown \|\| modelTier >= floorTier`) to clamp models up to a safety floor. The new registry keys models as `vendor/model@deployment` (e.g. `anthropic/sonnet-5@api` presumably) with a capability *vector*, not a scalar. The plan states the shim will map legacy names to registry entries but never states which registry row `"sonnet"` resolves to when multiple Sonnet deployments exist, nor how the shim reconstructs a total order for `applyFloor`'s `>=` comparison out of a vector space that Design Principles explicitly says "is a vector, not a scalar" (line 13). This is exactly a broken-lineage case the lens exists to catch: `applyFloor`'s safety-floor clamp is *itself* a downstream consumer of `ParseModelTier`, and the plan's Phase 2 acceptance criterion ("all existing routing tests pass via shim") can be satisfied by a shim that silently picks an arbitrary default deployment per legacy name, with no documented basis for the choice, and callers would never know.
- **Evidence:** Phase 2 acceptance (line 74): "all existing routing tests pass via shim; new table-driven tests cover vector matching, constraint blocks, unknown-provenance conservatism, each cost type; no callers outside the package touch tier integers" — this is a behavioral test, not a documentation requirement. Nothing in the acceptance criteria requires the shim's legacy-name → registry-row mapping to be written down anywhere a future reader (or `applyFloor`'s safety-floor logic) could audit.
- **Suggestion:** Phase 1's Registry v1 schema section (line 59) should require one explicit `legacy_alias` field per seed row claiming a bare-tier name (e.g. `legacy_alias: "sonnet"` on exactly one `anthropic/sonnet-5@*` row), with a Phase 2 acceptance bullet: "shim mapping is data-driven from `legacy_alias`, not hardcoded switch logic; ambiguous aliases (two rows claiming the same legacy name) fail config validation." Traces the shim to the same provenance discipline as the rest of the registry instead of exempting it as glue code.

### absent-vs-stale-conflated-in-provenance-vocabulary
- **Severity:** P1
- **Where:** §Design Principles line 36; §Phase 6 lines 99-104
- **What:** The plan's own decision lens (per this review's framing) requires distinguishing an absent standard from a drifted one — e.g. SWE-Bench Pro is explicitly "unreleased for Sol" (Problem section, line 13) versus a present-but-stale number. The three-value provenance tag (`benchmark \| judgment \| unknown`) has exactly one bucket for "we don't have a certified number" (`unknown`), and the plan states the router "treats `unknown` conservatively." But once a `benchmark`-tagged value exists and later becomes stale (superseded eval version, retracted result, vendor re-runs and revises), there is no tag transition defined — does it silently stay `benchmark` (falsely implying current certification), or does something demote it back toward `unknown`? If staleness silently keeps the `benchmark` tag, the router's "conservative on unknown" safety principle never fires for the actual dangerous case (a value that *used to be* trustworthy), only for the harmless case (a value that was never claimed). This is the precise "unbroken calibration chain" failure the lens is built to surface: a value that cannot be distinguished from its own stale self is not a datum.
- **Evidence:** Design Principles (line 36) defines only three tag states with no transition rules. Phase 6 (lines 99-104) adds a drift *report* but its acceptance criterion is "drift report runs clean against seed registry" — silent on what "drift" does to the provenance tag of the drifted field itself.
- **Suggestion:** Extend Phase 6's drift-report acceptance criterion (line 104) with: "fields flagged as drifted are automatically retagged from `benchmark` to `stale` (a new fourth provenance state) pending human re-certification; router treats `stale` at least as conservatively as `unknown`." Minimal: one new enum value, one retag side-effect in the drift script, one router rule addition — not a new phase.

### drift-report-has-no-obligated-disposition
- **Severity:** P2
- **Where:** §Phase 6 (lines 99-104); §Risks table (line 123, "Speculative registry rot")
- **What:** Phase 6's registry-refresh script "cross-checks registry cost/benchmark values against interrank, flagging drift (does not auto-write; provenance stays explicit)." This correctly avoids silent auto-correction (good — matches the human-gated design principle elsewhere), but "flagging" has no defined destination, urgency, or owner. Compare to Phase 5's evidence flow, which is fully specified (threshold detection → AskUserQuestion → approved write). Phase 6's flag could mean anything from a CLI printout nobody reads to a blocking CI check; the acceptance criterion ("drift report runs clean") doesn't distinguish "no drift found" from "drift found but nobody looked."
- **Evidence:** Line 103: "flagging drift (does not auto-write; provenance stays explicit)" — no destination or cadence specified, unlike Phase 5's fully-specified proposal flow (lines 94-97).
- **Suggestion:** One-line addition to Phase 6's bullet list: drift flags route through the same interspect evidence/proposal mechanism as Phase 5 (`constraint_block`-style event, human-gated review), rather than inventing a second, unspecified notification path.

### effort-conversion-table-authorship-unstated
- **Severity:** P2
- **Where:** §Design Principles, "Normalized effort knob" (line 38); §Phase 1 Registry v1 bullet (line 59, "effort mapping table")
- **What:** The effort-normalization table (abstract 1-5 → vendor semantics: Anthropic thinking budget, OpenAI reasoning_effort, n/a) is exactly the kind of cross-standard conversion table that needs its own provenance in a calibration-chain design — who asserts that Sol's `reasoning_effort: high` is equivalent to Fable's thinking-budget level 4? The plan lists it as a schema component (Registry v1, line 59) alongside capability vectors and cost types, which do get provenance tags, but the conversion table itself is never assigned a provenance/versioning discipline of its own.
- **Evidence:** Line 38 states the principle; line 59 lists "effort mapping table" as a Phase 1 deliverable with no provenance requirement attached, in contrast to capability vectors (explicitly provenance-tagged per line 36).
- **Suggestion:** Fold the effort mapping table under the same provenance-tag requirement as capability axes in Phase 1's schema spec — one sentence added to line 59.

## Verdict
The plan's provenance-tag design (`benchmark\|judgment\|unknown`) correctly handles the *absent*-standard case but has no lifecycle for a value that starts certified and later drifts — no recertification cadence, no stale-vs-fresh distinction, and the Phase 2 compat shim (a real downstream consumer of exactly this kind of un-provenanced re-basing) inherits the gap silently. These are small, schema-level fixes (one new provenance state, one cadence field, one data-driven shim table) rather than architecture changes, but skipping them means the registry's calibration chain is unbroken only until the first benchmark suite version bump — which, given Sol/Fable's 2026-07 vintage, is not a hypothetical.
