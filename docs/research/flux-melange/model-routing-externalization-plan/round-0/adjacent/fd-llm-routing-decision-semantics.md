## Findings

### no-vector-dominance-tiebreak
- **Severity:** P0
- **Where:** `docs/plans/2026-07-13-model-routing-externalization.md` lines 13-14 (problem statement introduces the vector), line 36 ("Capability vectors with provenance" principle), line 72 (decision function signature `(role, task_class, constraints, harness) → (model@deployment, effort, verification_gates[], rationale)`), line 74 (Phase 2 acceptance: "new table-driven tests cover vector matching")
- **What:** The plan's own motivating example is a non-dominated pair: "GPT-5.6 Sol breaks the ordering: ahead of Fable 5 on terminal execution (Terminal-Bench 2.1: 88.8 vs 83.4), behind on discernment and multi-file resolution (SWE-Bench Pro: unreleased vs 80.3)." This is presented as the reason a scalar tier is insufficient — but the plan never states what the decision function does when a task_class weights both axes and the two candidates are Pareto-incomparable. The decision function's output type includes a single winning `model@deployment`, meaning some tie-break must exist, but no comparison rule (weighted sum? lexicographic priority? per-task_class axis-priority table?) is specified anywhere in Design Principles or Phase 1/2.
- **Evidence:** Grepped `internal/routing/*.go` — the current `ModelTier` type (`routing.go` lines 6-14) is a plain `int` with `TierHaiku=1 … TierFable=4`, i.e., a total order by construction; there is no existing vector-comparison code to generalize from, confirming this is genuinely new decision logic the plan is deferring to "implementation." Phase 2's acceptance criterion ("table-driven tests cover vector matching") presupposes a spec to write tests against, but Phase 1's spec deliverable (line 56-64) lists only the three schemas (routing.yaml, registry, evidence) — no decision-algorithm spec. The three canonical task descriptors named in Phase 1's acceptance ("terminal grind, multi-file bugfix, client-confidential synthesis," line 64) are exactly the shape of task where Sol-vs-Fable non-dominance would surface, yet "hand-traced from the spec alone" cannot happen without a stated rule.
- **Suggestion:** Add one sentence to Phase 1's `routing.yaml` v1 schema item (line 58): task classes carry a per-axis weight vector or explicit axis-priority order, and the decision function's tie-break is "highest weighted-sum score; ties broken by declared axis priority list, first-listed wins." Include a worked trace of Sol vs. Fable 5 on the "terminal grind" descriptor as part of Phase 1's acceptance criterion, not deferred to Phase 2 test-writing.

### effort-normalization-no-equivalence-method
- **Severity:** P1
- **Where:** line 38 ("Normalized effort knob" principle), line 79 (Phase 3 `ic route explain` — "prints the decision rationale")
- **What:** The plan states abstract effort 1-5 maps to "Anthropic thinking budget, OpenAI reasoning_effort low→max/ultra, n/a for models without the dial" but never documents the equivalence method (is effort=3 "medium" by ordinal position, by some benchmark-matched compute-parity heuristic, or by whoever writes the table's judgment call?). Anthropic's thinking budget is a continuous token count; OpenAI's reasoning_effort is a 5-6 value discrete enum (low/medium/high/max/ultra per the plan's own naming). A linear 1-5 → discrete-enum mapping and a 1-5 → continuous-token mapping are different kinds of lossy projections, and the plan doesn't say which direction either one rounds.
- **Evidence:** No file in `docs/specs/` exists yet (confirmed via `ls`), so this table is wholly unwritten — the risk is that Phase 2's Go implementation invents the equivalence ad hoc without an agreed policy-layer method, same failure shape as the vector tie-break finding above. `ic route explain`'s stated purpose (line 79, "prints the decision rationale") does not mention surfacing the resolved vendor-native value, only "which axes, constraints, and rules fired" — so an operator debugging a quality regression on OpenAI has no way to see that effort=3 resolved to reasoning_effort=medium versus what it would have been on Anthropic.
- **Suggestion:** In Phase 1's registry schema item (line 59, "effort mapping table"), require each mapping row to state its rounding direction (e.g., "abstract effort rounds up to nearest vendor level") and add "resolved effort value (vendor-native)" as a required field in the Phase 3 decision JSON output, not just prose in `explain`.

### escalation-counter-scope-undefined
- **Severity:** P1
- **Where:** line 41 ("Two-strikes escalation encoded" principle), line 87 (Phase 4: "two-strikes escalation returns to planner")
- **What:** "Executor fails 2x or validator rejects 2x → escalate to frontier-tier re-scope" names no counting scope: per-task-attempt-chain, per-role-per-session, per-harness, or global. Phase 4 wires this into `codex-delegate.md`, which per the CLAUDE.md capability doctrine already governs parallel sub-agent spawns ("Spawns MUST pass an explicit model param" — implying parallelism is expected in this exact code path). Two independent executor attempts failing concurrently under an undefined-scope counter is a race: both read counter=0, both increment to 1, neither triggers escalation, and a third failing attempt proceeds without ever crossing the "2x" threshold as intended.
- **Evidence:** Grep across `internal/routing/*.go` and `docs/` for existing escalation-counter/state code returns nothing routing-specific (only unrelated privilege-escalation and generic "escalate to human" prose in other review docs) — confirming there is no existing state-management pattern this plan is reusing, so the gap is not covered by inherited discipline.
- **Suggestion:** Add an explicit scope declaration to Phase 1's evidence-event schema (line 60): escalation counting is scoped to `(role, task_class, session_id)` with the counter persisted as an evidence-event aggregate (queryable, not held in adapter memory), so concurrent Codex delegate sub-agents each emit `executor_failure` events that a single authoritative reader (not per-process memory) evaluates against the threshold.

### verification-gate-selection-single-case-only
- **Severity:** P2
- **Where:** line 40 ("Verification gates are routable outputs" principle), line 58 (Phase 1 schema item 1: "verification gates")
- **What:** The only worked example given is reward_hack_risk → behavioral-verify. The schema item in Phase 1 just lists "verification gates" as a field alongside roles/task classes/bindings/constraints/escalation rules with no indication it's a full rule table (risk-shape × task-class → gate × strictness) versus a single hardcoded special case generalized from the Sol reward-hacking flag mentioned in the Problem section (line 17).
- **Evidence:** The Problem section's only justification for verification-gate routing is the METR Sol flag (line 17); no other risk axis (e.g., long_context degradation, unknown-provenance targets) is connected to a gate anywhere in the document.
- **Suggestion:** Phase 1 acceptance criterion (line 64) should require the gate-selection rule to be demonstrated against at least two distinct risk shapes, not just reward_hack_risk, before Phase 2 treats it as implementable.

### benchmark-to-task-class-transfer-unstated-confidence
- **Severity:** P2
- **Where:** lines 13-14 (Problem statement), line 62 (Phase 1: "Sol/Fable capability rows sourced from the 2026-07 research... provenance-tagged")
- **What:** Terminal-Bench 2.1 and SWE-Bench Pro are specific benchmark distributions; the plan maps their scores directly onto task_class buckets like "terminal grind" and "multi-file bugfix" (the canonical descriptors named in Phase 1's acceptance, line 64) without stating whether that mapping is itself benchmark-validated (the task_class literally is the benchmark's task shape) or judgment-extrapolated (the task_class is a broader real-world category the benchmark merely correlates with). The plan's provenance tagging (line 36: "benchmark | judgment | unknown") applies to capability-axis *values*, but nothing tags the *mapping from benchmark to task_class* itself with a confidence level.
- **Evidence:** Design Principles line 36 defines provenance tags only for the capability values, not for the benchmark→task_class transfer function; Phase 1's acceptance (line 64) treats "hand-traced from the spec alone" as sufficient without requiring the trace to disclose transfer confidence.
- **Suggestion:** Extend the provenance tag set (or add a parallel field) to cover the task_class↔benchmark mapping itself, e.g. `task_class_source: benchmark-direct | benchmark-adjacent | judgment`, surfaced in `ic route explain` output per the CLI-contract lens's related finding.

## Verdict
The plan correctly diagnoses that a scalar tier can't express Sol-vs-Fable non-dominance, but never closes the loop with a stated comparison rule — this is the single highest-leverage gap because Phase 2's acceptance criterion ("table-driven tests cover vector matching") is unwritable without it, and the plan's own canonical task descriptors are chosen to expose exactly this ambiguity. Effort normalization and escalation-counter scope are the next-most load-bearing omissions; both are genuinely new mechanisms with no prior-art shim to fall back on.
