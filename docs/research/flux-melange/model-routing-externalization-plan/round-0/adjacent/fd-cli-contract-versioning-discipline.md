## Findings

### phase7-hermes-no-machine-checkable-schema
- **Severity:** P0
- **Where:** `docs/plans/2026-07-13-model-routing-externalization.md` lines 56-64 (Phase 1: "Write `docs/specs/routing-contract.md` defining the three schemas" — prose spec, no artifact format stated), lines 106-115 (Phase 7: "The validating case for the whole externalization: a harness that cannot read Clavain markdown")
- **What:** Phase 7 is explicitly framed as the test of whether the contract is independently implementable by a harness with no access to Clavain's markdown or, implicitly, to the Clavain/Codex adapter source code written in Phase 4. But Phase 1's deliverable is `docs/specs/routing-contract.md` — a markdown document defining three schemas in prose — with no mention of a machine-checkable schema artifact (JSON Schema, protobuf, or equivalent) that an independent implementer could validate against without a human reading and interpreting prose. If the Hermes adapter's author (per the plan's own team, working after Phase 4 already exists) in practice has access to the Clavain and Codex adapter implementations, the pilot's "success" would come from reverse-engineering those two implementations rather than from the spec alone — silently invalidating the phase's own stated purpose.
- **Evidence:** Confirmed via `ls docs/specs/` that no `docs/specs/` directory or prior schema-artifact convention exists yet in this repo to inherit from — this is a fresh decision point, not an established pattern being followed. The routing-overrides PRD this plan explicitly extends (`docs/prds/2026-02-15-interspect-routing-overrides.md`) also only documents its schema in prose (PRD line 26: "Schema documented: `version` (integer, starts at 1), `overrides[]` with `agent`, `action`...") with no JSON Schema artifact — meaning the plan is repeating the precedent's own gap rather than closing it, at the exact phase (7) designed to stress-test cross-implementation fidelity.
- **Suggestion:** Add a JSON Schema (or equivalent machine-checkable artifact) as a required Phase 1 deliverable alongside the prose spec, for at minimum the `ic route` decision-output JSON and the routing.yaml/registry/evidence schemas. Make Phase 7's acceptance criterion explicitly state that the Hermes adapter was built and validated against the schema artifact without reference to Clavain/Codex adapter source.

### decision-output-json-no-version-field
- **Severity:** P1
- **Where:** line 58 (Phase 1 schema item 1: "`routing.yaml` v1: ... Version integer; graceful degradation and env-var path override per the routing-overrides contract precedent"), line 78 (Phase 3: "`ic route` reads task descriptor (flags or JSON stdin), emits decision JSON")
- **What:** The plan is explicit and careful about versioning for `routing.yaml` (integer version, graceful degradation borrowed from the routing-overrides precedent) — but the decision-output JSON that `ic route` actually emits to every consumer (Clavain adapter, Codex adapter, eventually Hermes adapter) is never stated to carry its own version field or compatibility policy. This is the payload three independent harness adapters parse directly; if its field shape changes between Phase 4 (Clavain/Codex adapters written) and Phase 7 (Hermes adapter written against the spec), there is no stated mechanism for the Hermes adapter to detect it's looking at an unexpected shape versus a genuine schema evolution.
- **Evidence:** Line 58 names version integers for `routing.yaml`, and by extension (per the schema list structure) presumably for the registry and evidence schemas too — but the decision function's own output type, defined at line 72 as `(model@deployment, effort, verification_gates[], rationale)`, has no version field in its stated shape, and Phase 3's description of `ic route`'s output (line 78) doesn't mention one either.
- **Suggestion:** Extend Phase 1's schema list to explicitly include a fourth versioned schema: the `ic route` decision-output JSON, symmetric with the routing.yaml treatment, with the same version-integer + graceful-degradation policy.

### exit-codes-qualitative-not-enumerated
- **Severity:** P1
- **Where:** line 80 ("Exit codes: 0 decision, non-zero typed failures (constraint violation ≠ malformed input ≠ no-eligible-model)"), line 82 (Phase 3 acceptance: "constraint-violating descriptor exits non-zero with machine-readable reason")
- **What:** The plan correctly recognizes that different failure kinds need distinguishable exit codes ("constraint violation ≠ malformed input ≠ no-eligible-model") but never commits to a closed, numbered enumeration (e.g., exit 2 = constraint violation, exit 3 = malformed input, exit 4 = no eligible model). Without a fixed table, each harness adapter (Clavain shell wrapper, Codex adapter, eventual Hermes adapter) either has to parse the JSON output body to disambiguate failure kind (making the exit code itself nearly redundant) or ends up inventing its own numbering that the other consumers don't share — undermining the "composable, pure filter" design goal (line 78) for shell-level composition (`if ic route ...; then` patterns depend on stable, known exit codes).
- **Evidence:** Phase 3's acceptance criterion (line 82) only requires that a constraint-violating descriptor "exits non-zero with machine-readable reason" — this is satisfiable by any non-zero code paired with a JSON body, which doesn't test that the *code itself* is stable and enumerated, only that *some* signal exists.
- **Suggestion:** Commit to a specific, numbered exit-code table as part of Phase 1's contract spec deliverable (e.g., 0=decision, 2=constraint-violation, 3=malformed-input, 4=no-eligible-model, 5=schema-version-unsupported), and require Phase 3's acceptance criterion to check the specific code value, not just non-zero-ness.

### explain-output-stability-undesignated
- **Severity:** P2
- **Where:** line 79 ("`ic route explain` prints the decision rationale (which axes, constraints, and rules fired)")
- **What:** `explain` is defined purely as human-facing rationale text with no stability marking (stable/unstable) and no machine-readable alternative format named. Given that `ic route explain` is the only place several other findings in this review set point to as the natural home for richer diagnostic detail (resolved vendor-native effort value, task_class-to-benchmark transfer confidence), there's a real risk that a future consumer — one of the three independent harness-adapter maintainers — starts parsing `explain`'s prose output because it's the richest available signal and no machine-readable equivalent exists, and a later wording improvement then silently breaks that undocumented dependency.
- **Evidence:** No `--format=json` or equivalent flag is mentioned anywhere in the Phase 3 description (lines 76-82); the phase's acceptance criterion (line 82) only requires that `explain` "names the winning and losing candidates," which is satisfiable by unstructured prose.
- **Suggestion:** Either explicitly mark `explain`'s default output as unstable/human-only in the Phase 1 spec (freeing prose to improve without a version bump) and add a `--format=json` flag exposing the same rationale fields in the versioned decision-output schema, or fold rationale into the versioned decision JSON directly and drop the separate human/machine ambiguity.

### batch-input-mode-unscoped
- **Severity:** P2
- **Where:** line 78 ("`ic route` reads task descriptor (flags or JSON stdin), emits decision JSON. Pure filter; composable."), line 106-115 (Phase 7: Hermes Agent pilot)
- **What:** The contract is scoped to one task descriptor per invocation, with "composable" asserted but not qualified against the composition pattern most likely to actually be needed: a harness (Hermes on zklw, per Phase 7, or any future orchestrator) that needs to route a batch of many queued tasks. The plan neither commits to batch/stdin-stream support for v1 nor explicitly scopes it out with the tradeoff named (process-fork-per-task overhead vs. added stream-mode complexity) — leaving it to be discovered as an operational cost after consumers already depend on the single-input shape, which per the CLI-contract discipline this lens applies is exactly the kind of decision that becomes a breaking change once made post-hoc.
- **Evidence:** Phase 7's acceptance criterion (line 115) only requires "one real task routed" — consistent with single-invocation use, but doesn't test or reveal whether Hermes's actual task volume would stress the per-invocation model.
- **Suggestion:** Add one sentence to Phase 1's `ic route` contract section explicitly scoping batch/stream input out of v1 with the named tradeoff (accepting per-task process-fork overhead now, deferring stdin-stream mode until a consumer's task volume demonstrates it's needed), so the decision is deliberate and documented rather than implicit.

## Verdict
The plan's versioning discipline is strong for `routing.yaml` (explicit integer version, precedent-based graceful degradation) but that same rigor doesn't carry over to the artifact three independent harness adapters actually consume most directly: the `ic route` decision-output JSON and its exit codes. Phase 7's Hermes pilot is designed to prove independent implementability, but without a machine-checkable schema artifact and a closed exit-code enumeration committed in Phase 1, that phase risks validating "an implementer with access to the other two adapters can match undocumented behavior" rather than "the spec alone is sufficient" — undermining its own stated purpose.
