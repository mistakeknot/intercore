## Findings

### phase4-live-cutover-no-shadow-mode
- **Severity:** P0
- **Where:** `docs/plans/2026-07-13-model-routing-externalization.md` lines 84-90 (Phase 4: "Harness adapters (Clavain + Codex)"), line 90 (acceptance: "one real delegation flows end-to-end through `ic route` in each harness path; grep confirms no residual hardcoded model-name routing logic")
- **What:** The plan moves directly from Phase 2 (mechanism generalized, validated by unit tests) through Phase 3 (CLI surface, validated by round-trip demos) to Phase 4, where `clavain/commands/model-routing.md` and `clavain/agents/workflow/codex-delegate.md` are rewired to consume live `ic route` decisions for real agent delegation — and the acceptance criterion explicitly requires deleting the fallback ("doctrine prose deleted in favor of the spec," line 86; "grep confirms no residual hardcoded model-name routing logic," line 90). There is no stated shadow-mode or dual-run step where the new decision function's output is compared against the old capability-doctrine routing before the old path is removed. This is the plan's own capability-routing mechanism deciding which model runs every future Clavain/Codex delegation — a genuine hot-path cutover with the fallback deleted in the same phase as the cutover.
- **Evidence:** Phase 2's acceptance (line 74) validates the decision function only against unit tests and "no callers outside the package touch tier integers" — a structural check, not a behavioral comparison against production routing outcomes. Phase 3's acceptance (line 82) is three canonical descriptors traced by hand. Nothing in Phases 1-3 accumulates evidence that the new vector-matching logic (which the sibling decision-semantics lens notes has an unspecified tie-break rule) produces routing decisions equivalent-or-better than today's tier-based routing across the actual mix of real task classes before Phase 4 deletes the old path and grep-enforces its absence.
- **Suggestion:** Insert a shadow-mode step at the start of Phase 4: run `ic route` decisions alongside the existing doctrine-based routing for a stated window (e.g., N real delegations or M days), log divergences without acting on them, and require zero unexplained divergences (or a reviewed, accepted list of them) before deleting the doctrine prose and hardcoded logic. This is a bounded addition to Phase 4's acceptance criterion, not a new phase.

### compat-shim-no-removal-trigger
- **Severity:** P1
- **Where:** line 70 (Phase 2: "retain `ParseModelTier` as a compat shim mapping legacy names to registry entries (existing consumers keep working)"), line 124 (Risks table: "Compat breakage for legacy tier consumers | Phase 2 shim + full existing test suite as regression gate")
- **What:** The shim is introduced with open-ended language ("existing consumers keep working") and no removal deadline, no owning tracked item (bead), and no trigger condition (e.g., "remove when zero non-test callers remain" or "remove in the sprint after Phase 4 ships"). The Architecture Decision section's own stated discipline — "Prior art: routing was previously fragmented across `lib-routing.sh`, `agent-roles.yaml`, and `interserve classify`; consolidation into this package was the fix. Do not re-fragment." (lines 26-27) — is exactly the failure this shim risks recreating, except now as permanent dual-logic *inside* `internal/routing` rather than across packages.
- **Evidence:** Confirmed via `grep -n "ModelTier\|TierHaiku\|TierFable\|ParseModelTier" internal/routing/*.go` that `ParseModelTier` and the `ModelTier` int-enum type (`routing.go` lines 6-14, plus test coverage in `resolve.go:151-152`, `costs_test.go`, `resolve_test.go:285-293`) are load-bearing today across multiple files in the package, not a thin isolated wrapper — meaning "retain as compat shim" is retaining a moderately-sized surface (the whole existing `ModelTier` type plus its String()/parsing/comparison methods), and the plan gives no criterion for when the codebase has migrated enough callers off it to remove it.
- **Suggestion:** Add a removal trigger to Phase 2's acceptance criterion: create a tracked bead at shim-introduction time with an explicit condition ("remove when `grep -rn ModelTier --include=*.go | grep -v _test.go` outside `internal/routing` returns zero hits") and revisit at a stated checkpoint (e.g., "review at Phase 6" since Phase 6 already touches interrank/registry drift).

### phase5-7-no-evidence-integrity-gate
- **Severity:** P1
- **Where:** line 92-97 (Phase 5: "Feedback loop (interspect)"), line 106-115 (Phase 7: "Second-metaharness pilot"), line 126 (Risks: "Hermes evidence schema mismatch | Evidence schema defined in Phase 1 before any emitter exists; Hermes emits to the same store, no side channel")
- **What:** Phase 5's proposal flow "reusing the routing-overrides F2 pattern (threshold detection → AskUserQuestion with evidence summary → approved write)" and Phase 7's evidence emission both assume Phase 4's adapter emits evidence events correctly. Phase 4's acceptance criterion (line 90) is a single end-to-end delegation demo and a grep for absent hardcoded logic — it says nothing about evidence-event correctness (field completeness, correct `harness:` origin tagging, well-formed `executor_failure`/`validator_rejection` events). The listed mitigation for the *schema-mismatch* risk (line 126) addresses format compatibility, not data quality — a syntactically valid but semantically wrong evidence event (e.g., `harness` field defaulted incorrectly, or an event misattributed to the wrong role) would pass any schema check and still corrupt Phase 5's proposal input.
- **Evidence:** The routing-overrides PRD this phase explicitly reuses (`docs/prds/2026-02-15-interspect-routing-overrides.md`) has its own F3 acceptance criteria requiring write-validation ("read back and parse JSON to confirm validity," line 65) and dedup/atomicity guards on the *write* side — but nothing in that precedent or in this plan validates evidence-event *correctness* on the *read/ingest* side before it feeds a human-facing proposal. The human reviewing an AskUserQuestion proposal (per the F2 pattern) sees an evidence summary but has no signal distinguishing "high-quality evidence" from "several weeks of a mistagged harness field."
- **Suggestion:** Add an evidence-integrity check as an explicit Phase 4 or Phase 5 acceptance item: validate a sample of emitted evidence events against expected field population (non-null harness-of-origin, role, task_class) before Phase 5's threshold detection is allowed to consume them, and surface an evidence-quality indicator alongside the AskUserQuestion proposal summary.

### acceptance-criteria-all-single-demo
- **Severity:** P2
- **Where:** line 64 (Phase 1: "a routing decision for three canonical task descriptors... can be hand-traced"), line 74 (Phase 2: table-driven tests, but scoped to unit-test correctness not load), line 82 (Phase 3: "shell round-trip demos for the three canonical descriptors"), line 90 (Phase 4: "one real delegation flows end-to-end"), line 97 (Phase 5: "synthetic evidence stream produces a correctly-formed proposal"), line 104 (Phase 6: "drift report runs clean against seed registry"), line 115 (Phase 7: "one real task routed, executed, and evidenced end-to-end")
- **What:** Every phase's acceptance criterion is phrased as a single successful trace or demo ("one real delegation," "one real task," "shell round-trip demos for the three canonical descriptors") rather than including any regression or load dimension. `ic route` is described elsewhere in the plan as intended for composable, repeated invocation across every future agent delegation in Clavain and Codex paths (and per the CLI-contract lens's territory, potentially Hermes batch use) — a single-demo acceptance bar doesn't exercise concurrent invocation, malformed/adversarial task descriptors, or registry-loading failure modes.
- **Evidence:** No phase's acceptance criteria (lines 64, 74, 82, 90, 97, 104, 115) mentions concurrency, load, or adversarial-input testing; Phase 2 is the closest to a regression gate ("all existing routing tests pass via shim... no callers outside the package touch tier integers," line 74) but that is a structural compatibility check, not a correctness-under-load check of the new vector-matching path itself.
- **Suggestion:** For at minimum Phase 4 (the highest blast-radius transition, live cutover), add a regression dimension to the acceptance criterion: N concurrent delegations through `ic route` with no observed divergence from expected routing, in addition to the single-flow demo.

### no-aggregate-observability-deliverable
- **Severity:** P2
- **Where:** line 79 (Phase 3: "`ic route explain` prints the decision rationale"), line 99-104 (Phase 6: "Facts layer (interrank)" — drift report is scheduled, not evidence-driven)
- **What:** The only observability surface named anywhere in the plan is `ic route explain`, scoped explicitly to a single decision. No phase names an aggregate view (dashboard, alert, or even a log-aggregation query) over decision outcomes across time — e.g., what fraction of decisions hit the "unknown-provenance conservative" fallback, what the constraint-block rate is, or how escalation frequency trends. Phase 6's drift report is scheduled against interrank (facts layer), not against live decision-outcome distributions, so it wouldn't catch a misconfigured constraint silently routing an anomalous fraction of decisions into a conservative fallback path — each individual decision would look correct in isolation.
- **Evidence:** Phase 3 (lines 76-82) defines `ic route` and `ic route explain` with no mention of aggregate metrics emission; the Risks table (lines 119-126) lists six risks, none of which is "no aggregate observability," despite the plan's own trust-zone fail-closed design (line 37) meaning a fallback-rate spike would be silent and consequential (routing quietly getting more conservative/expensive) rather than loud.
- **Suggestion:** Add aggregate observability as an explicit Phase 5 or Phase 6 deliverable: minimally, a periodic (or evidence-triggered) report of decision-outcome distribution (fallback rate, constraint-block rate, escalation rate, per-role/per-harness breakdown), reusing the same evidence-store infrastructure Phase 5 already builds.

## Verdict
The plan's biggest migration-safety gap is the Phase 3→4 transition: it deletes the old routing path in the same phase it cuts over live agent traffic to the new one, with no shadow-mode comparison and only single-demo acceptance criteria, which is precisely the shape of change that ships clean and fails silently over weeks. The compat-shim's missing sunset and the evidence-integrity gap between Phase 4 and Phase 5/7 are the next-most consequential gaps, both because they compound: a shim with no removal trigger and a feedback loop with no evidence-quality gate both tend toward "permanently load-bearing, never revisited."
