## Findings

### provenance-tag-never-ages
- **Severity:** P2
- **Where:** Design Principles, "Capability vectors with provenance" (line 36); Phase 6 registry-refresh script (lines 99-104)
- **What:** The provenance tag on a capability-vector value is a flat three-way enum — `benchmark | judgment | unknown` — with no attached timestamp or rotation-number. A `terminal_execution` score tagged `benchmark` from the Phase 1 seed (July 2026, Terminal-Bench 2.1) is schema-indistinguishable from a `benchmark` value re-verified last week. This is a coppice steward who marks a coup "planted" but never records *which year* — every stand in the wood looks equally young forever, so nobody can tell a first-rotation oak from an eighth-rotation one by looking at the tag alone. The router "treats unknown conservatively," but a rotting `benchmark` tag isn't `unknown` — it's worse: it reads as more authoritative than a fresh `judgment` call while silently drifting out of date. Phase 6's drift report is the only check, and it "flags drift" but the plan states no cadence for running it and no rule for what a value does after N consecutive flagged-but-unfixed drift cycles (does it downgrade to `judgment`? to `unknown`? stay `benchmark` forever?).
- **Evidence:** Line 36: "Every value tagged `benchmark | judgment | unknown`." Line 62: "Sol/Fable capability rows sourced from the 2026-07 research... provenance-tagged" — no date field mentioned alongside the tag. Line 102: "Add a registry-refresh script cross-checking registry cost/benchmark values against interrank, flagging drift (does not auto-write; provenance stays explicit)" — flags but does not re-tag or expire.
- **Suggestion:** Add a `verified_at` (or `rotation`) field alongside the provenance enum in the registry v1 schema (Phase 1). Define one rule in Phase 6: a `benchmark` value untouched for N drift-report cycles auto-downgrades to `judgment` (or at minimum surfaces as a distinct "stale-benchmark" state to the router) rather than remaining indistinguishable from a fresh one. One field, one downgrade rule — not a new subsystem.

### escalation-ratchet-no-return-path
- **Severity:** P2
- **Where:** Design Principles, "Two-strikes escalation encoded" (line 41); Phase 4 acceptance criteria (line 87)
- **What:** "Executor fails 2x or validator rejects 2x → escalate to frontier-tier re-scope" is stated as a one-directional rule. This is distinct from the already-flagged registry entry/exit asymmetry (which is about rows in the registry never being culled) — this is about *escalation state* for a task class or role binding. Once a task class has been escalated to frontier tier following two strikes, the plan never says what happens next: does the *next* instance of that task class start at frontier tier again (permanent felling-up, monoculture-by-ratchet toward the scarce/expensive tier), or does it reset to the normal rotation and re-earn escalation independently? Coppice practice never permanently promotes a coup to old-growth reserve status after one bad felling season — the rotation resets. Absent a stated reset rule, the natural silent-default reading of "escalate" is sticky: every task class that ever hits two strikes ratchets the whole downstream population toward frontier tier over time, which is exactly the scarce-capacity misroute the capability doctrine (CLAUDE.md, "Model Routing — Capability Doctrine") exists to prevent, and which the plan's own two-strikes rule is supposed to be a *guarded exception* to, not a one-way valve.
- **Evidence:** Line 41: "Two-strikes escalation encoded. Executor fails 2x or validator rejects 2x → escalate to frontier-tier re-scope; never raise effort on a discernment-limited model." No de-escalation, reset, or re-evaluation clause anywhere in Phases 4–7 or the evidence schema (Phase 1 event types: `executor_failure`, `validator_rejection`, `cost_anomaly`, `constraint_block` — no `de_escalation` or `escalation_expired` event).
- **Suggestion:** State explicitly in the Phase 1 spec (routing.yaml escalation-rules section) whether escalation is per-invocation (resets every task) or persists per task-class/binding, and if persistent, define the return-to-rotation trigger (e.g., N consecutive successes at frontier tier before re-trying normal tier, or explicit human-gated reset via the same interspect proposal flow used for policy edits). One sentence in the spec closes this.

### schema-version-graceful-degradation-is-a-standing-deadwood-rule
- **Severity:** P3
- **Where:** Risks table, "Contract drift" mitigation (line 121); Phase 1 routing.yaml description (line 58)
- **What:** "Version integer; graceful degradation and env-var path override... consumers ignore-with-warning on unknown versions" plants a permanent policy, not a temporary one: every future schema version bump is designed to be silently tolerated forever by older consumers. This is a distinct isomorphism from the already-flagged registry-row seed/cull asymmetry — that one is about *data rows* accumulating without removal; this one is about the *degradation policy itself* being standing deadwood with no sunset. A pre-modern coppice steward who declares "if a coup looks unfamiliar, work around it and don't ask why" as permanent standing policy, rather than a temporary bridge during a specific transition, ends up with a wood where nobody ever learns which stands are running which rotation, because the tooling was built to never notice. Over 7 phases and multiple consumers (intercore, clavain, interflux, interspect, eventually Hermes), "ignore-with-warning" compounds: each consumer silently degrading on each other's version bumps means the contract can drift indefinitely with only a warning log nobody is proven to read.
- **Evidence:** Line 121: "Single spec doc (Phase 1) is canonical; version integers in every schema; consumers ignore-with-warning on unknown versions." No expiry, no "warnings become errors after N versions," no owner named for monitoring the warning stream.
- **Suggestion:** Not a blocker, but worth one line in the Phase 1 spec: name where the ignore-with-warning log surfaces (does it reach a human, or rot silently in a consumer's stderr nobody tails?) and consider a ratchet — warn for 1 version behind, fail closed for 2+ — so the graceful-degradation policy itself has a felling rule instead of being an unconditionally standing exemption.

## Verdict
The lens's already-hot regions caught the big-ticket entry-without-exit asymmetries (registry rows, the compat shim, floating Phase 7). What's left uncovered is one level more subtle: the *tags and states* the plan attaches to those artifacts — provenance labels, escalation state, and the degradation policy itself — carry the same plant-without-fell structure but at the metadata layer rather than the artifact layer. None of these are P0/P1; the plan's core mechanism is sound and these are single-field or single-sentence additions to the Phase 1 spec, not architecture changes.
