## Findings

### provenance-tag-has-no-flower-date

- **Severity:** P1
- **Where:** Design Principles line 36 ("Capability vectors with provenance... Every value tagged `benchmark | judgment | unknown`"); Phase 1 line 62 (seed values "sourced from the 2026-07 research... provenance-tagged").
- **What:** The provenance axis has exactly three values and none of them carries a when. A dyer reading the vat's flower doesn't just ask "did I ever see a flower on this vat" — she reads it *now*, because the flower fades, the temperature drifts, the reduction exhausts on its own clock independent of whether anyone re-tests it. The plan's provenance tag is the opposite: `benchmark` is a permanent credential, not a dated observation. Once a row is stamped `benchmark`, the router has no way to distinguish a capability score verified this morning from one verified at Phase-1 seed time six months prior and never revisited. Phase 6's drift report (line 102) is the closest thing to a re-read, but it runs on interrank's own cadence, not at decision time, and its job is to flag *disagreement* with interrank, not to age out a stale `benchmark` tag into something more conservative. A vendor can silently reweight `openai/gpt-5.6-sol@api` (already flagged elsewhere as an unversioned live target) and the registry row still says `benchmark`, still outranks `judgment`-tagged competitors, and the decision function has no signal that the sign it's reading is old dye, not fresh flower.
- **Evidence:** `routing.yaml` v1 schema fields listed at line 59 are "roles, task classes, per-harness bindings, constraints, escalation rules, verification gates" — no `as_of` or `verified_at` field anywhere in the three schemas named at lines 58-61. Decision function signature at line 72 takes `(role, task_class, constraints, harness)` — no staleness input, so it cannot even *penalize* an old tag if one existed.
- **Suggestion:** Add a `verified_at` (or `sourced_at`) field alongside the `benchmark|judgment|unknown` provenance tag in the registry schema (Phase 1, line 59). Smallest viable fix: no new mechanism needed — Phase 6's drift script (line 102) already touches every registry row; have it also emit a staleness warning (not just a value-drift warning) for `benchmark`-tagged rows older than some threshold, surfaced the same way unknown-provenance is already surfaced. One field, one extra check in an already-planned script.

### canary-precedent-dropped-at-the-loom

- **Severity:** P1
- **Where:** Phase 5 lines 92-97, explicitly "reusing the routing-overrides F2 pattern (threshold detection → AskUserQuestion with evidence summary → approved write)."
- **What:** This project already solved "how do I know a proxy-verified decision actually took" once, for a structurally identical problem: `docs/prds/2026-02-15-interspect-routing-overrides.md` F3 requires that every approved override spawn a canary — "20-use window or 14-day expiry" — that watches post-commit behavior and alerts if quality degrades ("Routing override for {agent} may have degraded review quality," PRD line 123). That canary *is* the airing step: the override is committed (agent excluded) on an inferred signal (evidence pattern, not ground truth), and only the canary's post-hoc monitoring reveals whether the exclusion was fugitive. Phase 5 of this plan names that exact PRD as its reused pattern but the acceptance criterion at line 97 stops at "approved proposal lands a valid `routing.yaml` edit" — it inherits the propose/approve half of F2/F3 and is silent on whether it inherits the canary half. A `routing.yaml` edit that reroutes `executor` for `task_class: terminal_grind` off a discernment-limited-but-cheap model is exactly the same shape of irreversible, proxy-verified, quality-affecting write as an agent exclusion — and the sibling system already knows this needs a monitoring window, not just a commit.
- **Evidence:** PRD F3 line 64: "canary record (20-use window or 14-day expiry) are inserted AFTER successful git commit"; PRD F4 line 76: "Canary verdict if available (PASSED, ALERT: quality degraded...)". Plan Phase 5 acceptance (line 97) has no analogous verdict step — "approved proposal lands a valid routing.yaml edit; rejected proposal leaves policy untouched" is the full acceptance surface, silent between commit and any confirmation the routing change performed as inferred.
- **Suggestion:** Phase 5's execution-grade task plan should explicitly state whether `routing.yaml` writes get a canary (reusing `mod_type` + canary tables already in interspect.db per the PRD) or explicitly declare why they don't need one — don't let the omission be implicit. If canary reuse is out of scope for Phase 5, say so as a stated non-goal so it isn't silently assumed solved by analogy to the PRD it cites.

### deployment-key-has-no-batch-identity

- **Severity:** P2
- **Where:** Design Principles line 35 ("Deployment-keyed registry. Unit is `vendor/model@deployment`... Same weights, different deployment = different routing target"); Phase 3 lines 76-82 (`ic route` decision JSON).
- **What:** `vendor/model@deployment` identifies the vat, correctly distinguishing cost/trust by hosting location. But it names the vat, not the dip. A decision made against `openai/gpt-5.6-sol@api` at 09:00 and another against the same key at 17:00 are represented identically in the decision JSON (line 78-82) even for an API deployment whose underlying weights the vendor controls and can roll without the registry knowing (this is the unversioned-live-target concern already flagged elsewhere at §phase 4/§risks — but the follow-on point, not yet raised, is narrower and purely representational: the decision record itself has no field to distinguish "which dip this was"). If a later `ic route explain` (line 82) or an interspect evidence event (Phase 5) needs to correlate a bad outcome back to *which* underlying model version produced it, there is no batch-level identifier in the decision output to anchor that correlation — only the deployment key, which is stable across silent vendor-side changes.
- **Evidence:** Decision function signature, line 72: return type is `(model@deployment, effort, verification_gates[], rationale)` — no timestamp or version-witness field. Evidence event v1 (line 60) lists event types (`executor_failure`, `validator_rejection`, `cost_anomaly`, `constraint_block`) with a `harness-of-origin field` but the plan doesn't specify the evidence event also carries the exact decision it's reporting against.
- **Suggestion:** Low-cost addition, not a redesign: have `ic route`'s decision JSON include a `decided_at` timestamp (distinct from the registry's `verified_at` proposed above) so that evidence correlation and any future drift investigation can bucket outcomes by "before/after" a suspected silent vendor change, without needing new registry mechanism.

## Verdict

The plan's registry treats `benchmark` provenance as a permanent credential rather than a dated reading, and Phase 5 cites the routing-overrides PRD's canary pattern by name while adopting only its propose/approve half — leaving the actual airing step (does the committed routing decision hold up after real use) unaddressed even though the project already built that exact mechanism once for a structurally identical proxy-verified commit. Both are one-field, no-redesign fixes; the second is the sharper miss because it's a citation gap, not an absent idea — the plan points at its own precedent and stops short of the part that matters.
